# CanvasKit V10 Opt-in Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a backend-neutral, local-first synchronization API that queues durable local documents, synchronizes them through an injected adapter, and requires explicit conflict resolution.

**Architecture:** `SyncController` sits above `PersistentEditorSession`: it stores uploads in a host-owned outbox before any remote call, pulls remote revisions, and removes entries only after an acknowledgement. `SyncAdapter` owns remote I/O; `SyncQueueStorageAdapter` owns durable queue/revision state. Conflicts are immutable controller state until a host explicitly accepts remote content, retains local content, or provides a merged document.

**Tech Stack:** TypeScript 5.8, Vitest 3, Playwright, Vite, pnpm/Turborepo, existing CanvasKit Scene V7 serialization and `PersistentEditorSession`.

**Spec:** `docs/superpowers/specs/2026-09-14-v10-opt-in-sync-design.md`

## Global Constraints

- V10 has no backend, provider SDK, credentials, browser database, network listener, automatic merge, CRDT, presence, or encryption.
- All remote and host-provided scene payloads must be validated with existing `loadScene` before they modify an open session.
- Queue entries survive retryable failures and `SyncController.dispose()`; acknowledgements remove only their own operation.
- Core must not read, mutate, or delete V9 recovery-journal data.
- Keep public API framework-neutral; React and Vue receive no V10-specific API.
- A major release includes focused unit tests, browser E2E, docs build, release gates, three screenshots, a 5–15 second GIF, release notes, and the repository release checklist.

```ts
export interface SyncQueueStorageAdapter {
  list(documentId: string): Promise<readonly SyncOutboxEntry[]>
  enqueue(entry: SyncOutboxEntry): Promise<void>
  remove(operationId: string): Promise<void>
  loadRevision(documentId: string): Promise<SyncDocumentRevision | undefined>
  saveRevision(revision: SyncDocumentRevision): Promise<void>
}

export interface SyncAdapter {
  pull(input: SyncPullRequest): Promise<SyncPullResult>
  push(entry: SyncOutboxEntry): Promise<SyncPushResult>
}

export type SyncPushResult =
  | { readonly status: 'acknowledged'; readonly revision: SyncDocumentRevision }
  | { readonly status: 'conflict'; readonly remote?: SyncRemoteDocument }
  | { readonly status: 'retryable-error'; readonly message: string }
```

Freeze every returned record and clone caller-owned documents before storing. `createMemorySyncAdapter(initial = [])` must maintain a private document/revision map and operation acknowledgement map; its `push` compares `entry.baseRevision` with the current revision and never mutates the caller entry.

- [ ] **Step 3: Implement queueing and the success path**

`queueDocument` must locate the open session document and kit, serialize the canonical current scene, read the saved revision from `queue.loadRevision(id)`, and call `queue.enqueue` before reporting `queued`. Generate IDs with an injected `createOperationId` option (default `crypto.randomUUID()` with a deterministic fallback) so tests can assert order.

`syncDocument` must serialize concurrent calls per document through a `Map<string, Promise<boolean>>`, then execute this sequence: load the oldest entry; set `syncing`; call `adapter.pull`; push the entry only if pull has no newer revision; save the acknowledgement revision; remove exactly that operation ID; set `synced`. A missing entry returns `false` and leaves an `idle` snapshot.

Run: `pnpm vitest run packages/core/test/sync.test.ts`

Expected: FAIL because conflict snapshots and `resolveConflict` do not exist.

- [ ] **Step 3: Implement non-destructive conflict detection**

On a pull result whose revision differs from the entry base revision, and on a push `{ status: 'conflict' }`, retain the entry and save a frozen conflict record. Validate any remote document with `loadScene` before placing it in the conflict snapshot. Invalid remote data must set `error`, retain the outbox entry, and never change the session.

- [ ] **Step 4: Implement and test each resolution exactly**

```ts
type SyncConflictResolution =
  | { readonly kind: 'accept-remote' }
  | { readonly kind: 'keep-local' }
  | { readonly kind: 'merge-document'; readonly document: StoredDocument }
```

For `accept-remote`, require valid remote content, save it through the session storage path, reopen/replace the active document safely, save the remote revision, then remove the conflicted entry. For `keep-local`, replace the entry with a new operation ID and the remote revision as `baseRevision`. For `merge-document`, validate the supplied scene and ID, persist it locally, and enqueue it against the remote revision. Test absent remote content, invalid merge input, a local edit made while conflict UI is open, and all successful outcomes. Run: `pnpm vitest run packages/core/test/sync.test.ts`

Expected: PASS.
